# What Makes LLM Tokenization Slow?
- URL: https://healeycodes.com/what-makes-llm-tokenization-slow
- Added At: 2026-09-04 02:46:07
- Tags: #read #llm

## TL;DR
文章通过优化GPT-2分词器发现，性能瓶颈在于海量微小操作而非单步复杂度。采用直接处理字节、利用token ID与排名关系及边界向量后，BPE合并开销大幅下降，正则匹配成为新瓶颈。流式分词与并行化收益有限。

## Summary
这篇文章围绕“为什么 LLM 的 tokenization 会慢”展开，作者以 GPT-2 的参考编码器为研究对象，将其移植到 Rust 并尝试多种优化，最终揭示了 tokenization 的性能瓶颈所在。下面带你逐步理解文章的内容和关键发现。

---

### 1. 背景：Tokenization 在 LLM 调用中的位置

LLM 接收的不是原始文本，而是 token ID 序列。例如 GPT-2 的 tokenizer 会把 `what's the weather in goldshire?` 编码成 `[10919, 338, 262, 6193, 287, 3869, 10932, 30]`。

虽然 tokenization 只占整个 LLM 调用延迟的一小部分，但它处于“热路径”上，而且在某些产品中可能被多次调用（例如判断是否需要压缩上下文、估算成本、路由提示词等）。因此它的性能依然值得关注。

---

### 2. GPT-2 的 Byte-Pair Encoding（BPE）原理

GPT-2 使用字节对编码（BPE），将任意 UTF-8 文本转换为可逆的 token ID 序列。流程如下：

- **预分词（regex 分割）**：先用一个正则表达式把输入分成多个独立的区域，比如单词、数字、缩写、标点、空白等，避免 BPE 跨过明显的文本类型边界。
- **字节级基础字母表**：GPT-2 需要所有 256 个字节值作为基础符号，以便表示任意 UTF-8 文本（包括无效的独立字节）。这些字节会被映射成可见的 Unicode 符号（例如 `é` 的字节 `c3 a9` 显示为 `Ã©`）。
- **合并规则**：`vocab.bpe` 文件列出了所有可合并的字节对，按优先级排序。合并时总是选择**当前相邻对中排名最低（即优先级最高）**的那一对，而不是从左到右扫描。
- **最终 token 映射**：合并完成后，得到的每个字节序列会在 `encoder.json` 中查找对应的 token ID（GPT-2 词汇表包含 256 个基础字节 token 和约 5 万个合并 token）。

以 `goldshire` 为例，它的合并过程需要 8 轮，最终得到两个 token：`Ġgold`（ID 3869）和 `shire`（ID 10932）。

---

### 3. 基准版本：直接移植 Python 参考实现

作者将 OpenAI 的 `encoder.py` 几乎原样移植到 Rust，保留了相同的正则、字节映射、合并排名和词汇表。关键点是：

- 每个正则匹配到的片段会独立进行 BPE 合并。
- 合并循环会反复扫描整个片段，找出排名最低的相邻对，执行合并，然后再扫描，直到没有可合并的对为止。
- 为了模拟生产环境，作者用 LRU 缓存（上限 256 条）代替了 Python 参考实现的无界缓存。

**基准性能**（在 M1 Pro 上，输入为 32 KiB 的《白鲸》和 8 MiB 的 React 源码）：

| 版本 | Moby-Dick 32 KiB | React 8 MiB |
|------|------------------|-------------|
| Python encoder.py | 42.43 ms（0.7 MiB/s） | — |
| Rust 基线 | 7.01 ms（6.0 MiB/s） | — |

虽然 Rust 版本已经比 Python 快很多，但合并循环的低效之处在于：每执行一次合并，就要重新扫描整个片段，即使大部分内容没有变化。

---

### 4. 第一次优化尝试：优先队列 + 链表（V2）

作者尝试用**最小优先队列**和**链表结构**来避免全量重扫：

- 优先队列始终弹出当前排名最低的候选对。
- 链表记录相邻关系，合并后只需要更新受影响的两个邻居。
- 弹出的候选对可能因为之前的合并而失效，因此需要重新检查。

**结果出乎意料：性能不升反降。**

| 版本 | Moby-Dick 32 KiB | React 8 MiB |
|------|------------------|-------------|
| Rust 基线 | 7.01 ms | 6.0 MiB/s |
| 堆 + 邻居 | 9.25 ms | 5.4 MiB/s |

原因在于：正则匹配出的片段通常非常小。统计显示，平均片段长度只有约 4~5 字节，最大也不过几十字节。在这么小的尺度上，线性扫描连续内存的成本极低，而堆带来的额外开销（哈希映射、过期条目、间接寻址、分支等）无法被抵消。OpenAI 的 `tiktoken` 实际上也采用了类似的策略，但只对长度超过 100 字节的片段使用堆和紧凑状态路径。

---

### 5. 第二次优化：直接处理字节（V3）

受到 `tiktoken` 的启发，作者彻底改变了合并的内部表示：

- 在初始化时，将 `encoder.json` 中的 token 字符串**解码回原始字节**。
- 利用 GPT-2 词汇表构造的一个关键性质：**ID 0~255 是基础字节 token；学习到的合并 token 按合并顺序获得后续 ID，因此 token ID 减去 256 就是该合并的零基排名**。也就是说，**token ID 越小，合并优先级越高**。
- 这样，合并时可以不再处理 Unicode 符号，而是直接操作原始输入字节的**偏移范围**。

具体实现：

- 对每个正则匹配片段，如果片段整体已经是一个已知 token（如 `the` 或 `wow`），直接返回其 ID，跳过 BPE 过程。
- 否则，维护一个**边界向量**，存储当前各个 token 片段的起始偏移。
- 每次合并时，找到排名最低的相邻候选（通过查词汇表得到），删除对应边界，更新左右邻居的候选排名。
- 所有合并完成后，根据最终边界切分出字节片段，再查词汇表得到 token ID。

这种做法的好处：

1. **不需要为中间合并结果分配新字符串**，直接借用原始字节切片。
2. **合并过程只是移动/删除边界索引**，内存紧凑。
3. **哈希表使用 `FxHashMap`**，比 Rust 默认哈希更快。

**性能结果：**

| 变体 | Moby-Dick 32 KiB | React 8 MiB |
|------|------------------|-------------|
| V3（先查词汇表） | 3.09 ms（9.4 MiB/s） | — |
| V3（先查缓存） | 3.23 ms（8.8 MiB/s） | — |
| tiktoken-rs r50k_base | 2.15 ms（11.7 MiB/s） | — |

相比 Rust 基线，V3 对 Moby-Dick 快了约 2.3 倍，对 React 快了约 1.6 倍。即使如此，仍然略慢于专门优化的 `tiktoken-rs`。

---

### 6. 各阶段耗时分布与根本原因

作者进一步分析了不同版本中各阶段的耗时占比（V1、V2、V3）：

| 阶段 | V1 Moby | V2 Moby | V3 Moby | V1 React | V2 React | V3 React |
|------|---------|---------|---------|----------|----------|----------|
| regex 匹配 | 29% | 20% | **55%** | 39% | 35% | **55%** |
| 字节映射 | 4% | 3% | 9% | 6% | 5% | 9% |
| 缓存 | 3% | 2% | 10% | 4% | 4% | 8% |
| BPE 合并 | **51%** | **69%** | 9% | **40%** | **47%** | 8% |
| 查找/输出 | 13% | 6% | 17% | 11% | 10% | 20% |

可以清楚看到：

- 在最初的版本中，BPE 合并是最大的瓶颈。
- 经过 V3 优化后，合并开销大幅降低，**regex 匹配成为最主要的耗时点**。

**核心结论**：Tokenization 之所以慢，并不是因为某一步复杂，而是因为它需要在大量非常小的文本片段上执行海量的微小操作（正则匹配、查找、合并）。这些操作单次成本很低，但数量极大，累积起来就成了性能瓶颈。

---

### 7. 其他思考与启发

- **粗略估算 token 数量**：如果只需要大致大小，可以用 `输入字节数 / N` 来估算，完全跳过 tokenization，几乎零成本。
- **流式 tokenization 的复杂性**：如果输入是分块到达的，不能简单地把每块的 token 数相加。因为后面的块可能会改变前面块的正则分割边界，或者完成前面块未完成的 BPE 合并。例如 `count(" goldshi") + count("re")` 不等于 `count(" goldshire")`。`tiktoken` 提供了 `encode_with_unstable` 来处理这种“稳定 token + 可能的补全序列”的情况。
- **并行化收益有限**：虽然正则匹配的片段可以独立处理，但由于片段太小，并行调度和协调的开销往往会抵消收益。作者使用 Rayon 并行处理正则匹配的实验结果只是略有提升，且性能不稳定。
- **通用性**：这些发现主要基于 GPT-2 的字节级 BPE，但现代 tokenizer 虽然可能在词汇表、归一化、正则、特殊 token 规则上有所不同，底层的工作模式是相似的。

---

### 总结

这篇文章通过实际移植和逐步优化 GPT-2 tokenizer，揭示了 tokenization 的性能瓶颈在于**大量微小的操作**，而非单个复杂步骤。最终优化方案（直接处理字节、利用 token ID 与排名的关系、边界向量）将 BPE 合并的开销大幅降低，使正则匹配成为新的主要瓶颈。文章还讨论了流式 tokenization、粗略估算和并行化等实际问题，提供了对 tokenizer 性能优化的深入见解。
