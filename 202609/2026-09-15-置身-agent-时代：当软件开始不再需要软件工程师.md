# 置身 Agent 时代：当软件开始不再需要软件工程师
- URL: https://www.bmpi.dev/dev/agent-era-software-engineering/
- Added At: 2026-09-15 14:01:52
- Tags: #read

## TL;DR
文章借两个复杂项目观察：智能体正接管编码、评审、测试与故障排查，人转向产品、成本、体验和责任等关键决策，注意力成瓶颈，经验变风险控制。核心追问：复杂软件还需同样多工程师吗？未来有经验者从何而来？

## Summary
这篇文章的核心，是作者用自己的两个长期业余项目做样本，观察一件事：当 Agent 承担了越来越多软件工程工作之后，一个软件项目到底还需要多少软件工程师。它的结论不是“AI 会不会取代程序员”这种老问题，而是把问题推进了一层——复杂的软件，是否还需要和过去一样多的软件工程师？以及，如果未来只需要少数有经验的人带着一群 Agent 工作，这些“有经验的人”又是从哪里来的？

下面按文章的推理脉络来梳理。

**一、作者的个人转变：从 Review 防线到退出实现层**

2023 年作者写 ChatGPT 结对编程时，判断很明确：AI 能写代码，但会幻觉 API、误解上下文、遗漏边界，所以 Human Review 是最后一道防线。只要人还要理解实现、判断代码是否正确，软件工程师的核心价值就还在。

三年后，他发现自己已经很少做这件事了。现在他的开发循环大致是：和 ChatGPT 讨论产品方向和工程约束，把任务交给 Codex、Claude、DeepSeek、GLM 等 Coding Agent；Agent 读仓库、查 issue、实现、跑测试、修 CI；完成后由另一个模型 Review；有问题就发回实现 Agent 修；直到 Reviewer 认为没有 blocker，然后合并。这个循环里经常没有他对代码的逐行 Review。

也就是说，2023 年他认为不可跨越的 Human Review 防线，现在本身也开始由另一个 Agent 承担。他的角色从“设计 → 写代码 → 测试 → Review”，变成了“决定要解决什么 → 看结果是否值得接受”。甚至连“把 Reviewer 意见复制给 Coding Agent”这个动作，都开始被 computer-use Agent 替代。

**二、两个样本为什么值得认真对待**

作者强调，如果这两个项目只是 CRUD Demo，后面的结论没有意义。所以先交代了它们的复杂度。

Free4Chat 最早是匿名 WebRTC 聊天室，后来迁移到 Cloudflare，加入了 Agent Runtime、权限系统、语音、临时任务、Live View、Room Apps。它的特点是“小而难”：让 Agent 真正在 Room 里开口说话，链路要穿过 SFU、本地 Agent Runtime、Pion、STT、ACP Harness、TTS、音频处理、publication、Cloudflare SFU，最后从另一个人的浏览器播放出来。问题经常只有在真实浏览器、真实 SFU、真实 Runtime、多设备一起跑时才暴露。一个看起来很小的功能，会同时跨过浏览器、WebRTC、Cloudflare、原生 Runtime、Agent Harness、授权和生命周期几层边界。

策引则是另一种复杂度：从一个投资组合和策略工具长成完整系统，覆盖行情数据、策略执行、回测、任务调度、组合指标、AI 分析、研究系统、邮件通知和基础设施。它还夹杂金融领域的正确性问题。比如 Sharpe Ratio 曾经漏掉了现金流调整，原始值接近 2，换成正确的现金流调整收益序列后只有 0.6 左右。这种 Bug 没有炫酷技术，但结果错了，整个产品就是错的。还有缓存过期问题，会一路牵扯 source freshness、retry amplification、cooldown ownership、Redis recovery 和多级缓存之间的数据优先级。

这两个样本，一个往技术深处走，一个往业务和系统宽度走，都已经复杂到不能简单当成 Vibe Coding Demo。

**三、风险结构变了，不是风险消失了**

作者特别防止一个误解：他不 Review 代码，不是因为 Agent 已经几乎不出错。Free4Chat 出现过 CI 全绿、PR 合并，然后首页直接不工作。多人真实测试也抓出大量自动化没覆盖的问题：浏览器随 Room 时间变长越来越卡、附件在不同设备读取失败、某些 Agent 收不到 @mention、手机和桌面看到的 Screen Share 不一致、一个十几 MB 的视频有人能收到有人收不到。WebRTC 尤其喜欢教育所有相信“测试已经全绿”的人。

所以现在的模式更接近：Agent 写，Agent Review，自动测试和真实运行一起不断暴露问题，Agent 再修；人接受这个系统不是数学上可靠的，只在真正重要的地方介入。Agent Review 不会创造正确性，它只是把 Review 本身也机器化了。经验仍然重要，但越来越少直接表现为亲手写出的代码，而更多表现为“知道什么地方不能随便相信”。

**四、连“发现问题”也开始被交出去**

另一个误解是：是不是作者仍然扮演真正的 Senior Engineer，由他发现问题、定义问题，然后让 Agent 去修？如果真是这样，变化其实没那么大，只是 Senior 多了一批便宜的执行者。但实际情况不是这样。

策引那个 Sharpe Ratio 问题，不是他拿公式检查报表时发现的。很多缓存、并发、安全问题也不是他先定义好再让 Agent 写代码。它们往往来自 Agent Review、自动测试、日志调查或生产异常后的系统性排查。比如生产任务报错，Slack 先收到告警。以前他得登录服务器、查日志、定位 job、检查 Redis、看队列、比对最近发布，慢慢把故障链串起来。现在很多时候他把错误交给 Agent，Agent 自己查日志、看部署状态、分析最近修改、检查相关缓存和队列，最后给他一份 incident report：发生了什么、在哪一层失败、是不是暂态错误、有没有数据损坏、是否需要修、怎么修。有时候他对这次事故的全部了解，就是最后读了这份报告。

这对他的冲击比“Agent 会写代码”大得多。写代码本来就是最容易被自动化的软件工程活动之一。但当 Investigation、Code Review、Test、Production Diagnosis 也逐渐变成 Agent 的工作，问题就不再只是“以后程序员还要不要自己写代码”，而是“软件生产过程中，到底还有多少环节必须有软件工程师持续参与”。

**五、人还剩下什么**

作者说，这不意味着他什么都不管了，恰恰相反，有些事情他管得更紧。

第一是产品方向。Free4Chat 到底是什么，不是 Agent 决定的。它很容易继续往功能上长：永久 Workspace、Agent 平台、账号体系、中央 Memory、任务管理、插件市场、远程桌面。这些方向每一个都能写出非常合理的 PRD。但他不想让它变成这些东西。Free4Chat 的价值恰恰是低成本、临时、无需永久 Workspace 的协作空间，Human 和 Agent 可以临时进来，各自带着能力，协作完就走。很多最重要的产品决策不是“加什么”，而是“不做什么”。Agent 很擅长回答“如何把这个需求实现得更完整”，但一个项目为什么存在、什么东西虽然可以做却不该做，仍然高度依赖人的价值判断和品味。

第二是成本。Free4Chat 是免费的，所以很多架构选择最终不是纯技术问题，而是现实问题：如果用户增长 100 倍，我愿不愿意付这张账单？他会看 Cloudflare Durable Object duration，算 SFU egress，看长期连接有没有破坏 hibernation，看一个功能是不是悄悄把高频数据写进存储。策引也一样，Fly.io、Cloudflare、模型 API、行情服务，最后都会变成信用卡上的数字。这时候他会突然重新变得像一个非常保守的架构师，因为 Agent 不会因为下个月 Cloudflare 扣钱而睡不着，他会。

第三是最终的人类体验。Voice Agent 的声音自然不自然，一个按钮放在那里是不是奇怪，手机上这个 Room 用起来是不是让人烦，等待三秒和等待八秒有什么区别。这些当然也可以做自动化测试、Browser Agent、Vision Model 打分，但他还是会自己打开它。毕竟这个软件最后还是给人用的，而他刚好是个人类。

最后是责任。账号是他的，服务器是他的，信用卡是他的，用户遇到问题最后找的也是他。Agent 可以提出判断、执行判断，但什么风险值得承担，仍然是他的问题。

所以他的总结是：人没有完全从软件生产里消失，而是从大量过程中消失，然后集中到少数高后果的决策点上。

**六、注意力成为新的瓶颈**

过去业余项目最大的限制是时间。想到一个功能，周末可能只剩四个小时，得自己设计、写、调试、测试。一个稍微复杂的功能做几周很正常。所以天然会控制 Scope，不是因为产品判断特别高明，而是因为根本写不过来。

现在这个约束明显变弱了。Agent 可以在他工作、吃饭甚至出去玩的时候继续实现、测试和修问题。周末有时候只需要集中看半天，剩下机器自己跑。于是新的瓶颈出现了：他根本看不过来。不是代码写不完，而是 Agent 生产出来的代码、PR、分析、issue、实验、Review 结果越来越多，他没有足够注意力逐个理解。这也解释了为什么“不亲自 Review 代码”最终几乎是必然的。如果机器一天可以产生几十个值得合并的修改，而人仍然坚持逐行读完，那么 Agent 的生产能力最终还是会被人的 Review 带宽锁死。

所以他现在主动区分：哪些东西值得花注意力？普通实现细节，不看。测试失败，Agent 自己修。一般 Review 意见，Agent 自己处理。偶发生产错误，先让 Agent 调查。但如果涉及成本突然上升、产品方向改变、权限边界变宽、架构开始失控，或者某个真实用户体验明显不对，他才会进去。

以前软件工程的稀缺资源是 Engineering Time，现在至少在这两个项目里，更稀缺的是 Human Attention。

**七、经验从生产能力变成风险控制**

一个自然的反驳是：你能这么玩，是因为你本来就是一个做了十几年软件的人。作者认为这个反驳是对的。

他虽然没有逐行 Review，但并不是完全不理解这些系统。Free4Chat 的整体架构边界、为什么要拆 Runtime 和 Harness、为什么 capability 不能等价于 authorization、为什么高频 App 数据不能走 Durable Object，他是知道的。策引为什么必须区分外部现金流和投资收益，为什么组合指标不能只看漂亮数字，为什么白盒策略比“AI 神秘预测”更重要，他也知道。这些经验决定了他更容易知道该问什么，哪些结果值得怀疑，什么设计虽然能 Work 但从根上就不该做。

文章引用了 Anthropic 2025 年 6 月的研究《Agentic coding and persistent returns to expertise》，分析了约 40 万个 Claude Code session。一个结果是：典型 session 里，人仍然承担大约 70% 的 planning decision，Claude 承担大约 80% 的 execution decision；更有经验的用户往往能让 Agent 在每次指令后完成更长的 action chain。经验仍然显著影响成功率。被判定为 novice 的 session，严格意义上的 verified success 只有大约 15%；intermediate 以上大致提高到 28%—33%。当任务已经遇到明显问题时，novice session 最后仍然成功的比例大约 4%，expert 可以达到 15%。这和作者的体验非常一致。

只是这种经验的作用已经不像以前那样直接。过去是：你不懂，所以你写不出来。现在越来越像：即使你不懂，Agent 也可能给你做出来；但你懂不懂，会影响你是否知道什么时候不能相信它。软件工程经验正在从一种直接生产能力，逐渐变成一种风险控制能力。

更有意思的是，Anthropic 的数据里，在真正产生代码的 session 中，软件相关职业的 verified success 大约是 34%，其他职业已经达到约 29%；如果把 partial success 也算进去，则分别是 89% 和 88%。如果这个差距继续缩小，那么软件生产可能逐渐变成所有职业中的一种普通活动，而不再天然属于一个单独的专业职业。作者认为这可能才是软件工程师真正需要担心的部分。不是 Agent 会不会写代码，而是“能够生产软件”这件事，本身是否还需要成为一个独立职业。

**八、软件工程本来就是为人设计的**

作者以前写过一系列 Google Software Engineering 相关的文章。其中一个他认同的观点是：Programming 和 Software Engineering 不是一回事。程序写出来只是开始。软件会存在很多年，会不断变化，会有越来越多人修改它。真正困难的是怎么让一个团队在时间和规模上持续安全地改变一个系统。

所以才有 Code Review、CI、Design Doc、Tech Lead、Ownership、On-call、Knowledge Sharing、Coding Convention 以及各种开发流程。这些东西当然有技术价值。但回头再看，会发现相当一部分其实是在解决一个问题：怎么让一群能力不同、信息不同、会犯错、会遗忘、会离职、沟通带宽有限的人一起维护一个复杂系统。

Code Review 不只是检查 Bug，它还传播知识。Design Doc 不只是记录设计，它让不同的人先形成共识。Coding Convention 不只是追求漂亮，它减少团队认知成本。On-call 和 Ownership 也不仅是 Debug 机制，它们首先回答“出了问题到底谁负责”。

过去默认：软件复杂度增长，最终一定需要更多人。人变多以后协调成本上升，于是 Software Engineering 这整套方法论出现，用来控制人的协作复杂度。但如果一个参与者可以同时读完整仓库、Issue、PR、日志和文档，不会因为今天请假漏掉上下文；如果它可以在几分钟内 Review 一个巨大 Diff；如果另一个 Agent 又可以重新独立 Review；如果它们不需要开会、不需要等第二天上班，也不存在“这个模块只有老王知道”这种组织记忆问题——那么过去一些理所当然的软件工程结构，至少会开始变得奇怪。

并不是所有流程都会消失，但它们原本优化的对象正在改变。

**九、2016 年的 Full Stack 和 2026 年的 Agent**

作者想到 2016 年写的《一款产品的从 0 到 1 之旅》。当时让他兴奋的是，一个人借助开源软件、云服务和 Full Stack 技术，已经可以把一款完整产品做出来。

但当年的“一人开发”是什么意思？是一个人自己做更多事情：自己设计、自己写 iOS、自己写 Backend、自己设计数据库、自己部署服务器、自己测试。Full Stack Engineer 的本质是：一个人会做整个 Stack。

十年后，Agent 时代的一人开发，不一定意味着一个人学会了整个 Stack，甚至可能恰恰相反：一个人越来越不需要亲自去做整个 Stack。这两个状态表面上都叫“一人开发”，背后的生产方式却完全不同。一个是人的技能边界不断扩大，另一个是软件生产开始脱离人的直接执行能力。从这个角度看，Full Stack Engineer 也许只是一个很有意思的过渡形态。

**十、样本的边界**

作者也把局限讲清楚。Free4Chat 和策引都是他的项目，没有大型组织、几十个团队、复杂审批链。很多事情他可以直接决定，做错了也主要由自己承担损失。所以他能够非常激进地把权限交给 Agent。

企业里显然没有这么简单。金融、医疗、大型基础设施和各种受监管系统，需要审计、责任分离、合规签字、变更审批。就算 Agent 技术上可以完成某件事，也不代表组织会允许它自己做。而且团队协作里的很多“摩擦”本来就不是纯粹的浪费。知识扩散、责任确认、多人 sign-off，本身也是风险控制和组织治理。

所以他并不认为两个 side project 已经证明未来所有公司只需要一个工程师。这两个样本真正有意思的地方，是它们接近一个低组织摩擦环境：一个人拥有比较完整的产品决策权、架构权和最终责任，又可以自由使用 Agent。在这种条件下，可以看到一个以前很难看到的东西：一个有一定复杂度的软件，为了持续演进，最低到底需要多少 Human Engineering Labor。

他看到的答案，比三年前想象得低很多。大型企业不会立刻达到这个下限，甚至可能永远不会。但这个下限本身一旦下降，就已经足够重要，因为市场最后会不断尝试逼近它。

**十一、当 Engineering 变得便宜**

更讽刺的是，当“做软件”越来越容易以后，作者没有觉得做产品变容易。Free4Chat 可以快速实现很多新能力，策引也可以不断增加实验、分析和自动化。但真正难的问题一个都没有消失：谁需要它？为什么要用？为什么愿意长期用？为什么愿意付钱？这个需求是真的，还是我自己觉得有意思？产品有没有 PMF？

这些问题没有因为 Coding Agent 变强而自动得到答案。某种程度上，问题反而更严重。以前很多产品不会出现，是因为做出来太贵。一个想法如果需要五个工程师做半年，很多人连试都不会试。现在同一个想法可能几天就能做出第一版。于是软件的供给会变得非常便宜，而需求没有同步增长。人的时间没有变多，钱包也没有变厚。这意味着 Agent 时代也许不是“每个人都有一个成功软件产品”，而是：世界上会突然出现多得多的软件，然后绝大多数软件仍然没人要。

Engineering scarcity 正在下降，Problem scarcity 没有。这也是为什么作者现在会比以前更频繁地砍掉 idea。既然实现越来越便宜，那么真正需要节约的就不再是代码，而是注意力和机会成本。

**十二、下一代 Senior 从哪里来**

这是作者目前没有答案的问题，也是全文最深的追问。

他今天能够这样使用 Agent，很可能确实和已经做了十几年软件有关。以前那些痛苦经历——自己 Debug 并发问题、自己看线上事故、Review 别人的代码、被别人 Review、做过错误架构然后再重构——共同形成了某种风险直觉。很多东西他甚至没办法写成 Checklist，只是看到一个设计，就觉得哪里不太对。

但这些经验过去是怎么产生的？过去一个 Junior Engineer 会亲手写大量代码，也会不断犯错。他会在 PR 里被 Senior 一遍遍指出问题，自己 Debug，遇到线上事故，再回头修改设计。几年下来，这些密集的反馈才慢慢变成经验，最后让他知道哪些地方最容易出错，哪些方案虽然局部合理，却会在长期把系统带向错误的方向。

如果未来最有效的软件生产方式变成 Agent 负责写代码、Review、Debug 和事故分析，而 Junior 更多只是在最后看到一句“tests passed”，那么这条经验形成路径就会发生很大的变化。十年以后，我们还能够期待这样的人自然拥有今天 Senior Engineer 的判断力吗？如果可以，这种判断力又会从哪里来？

这也许是 Agent 对软件工程行业最反常的长期影响之一。当前最有效的 Agent 工作流，似乎仍然非常受益于有经验的人；但这种工作流本身，却可能正在减少产生这些经验的机会。软件行业也许不仅在减少 Junior 岗位，它甚至可能在改变自己生产 Senior Engineer 的方式。

作者说，也许未来的工程经验会通过完全不同的路径获得——更多来自设计、评估、模拟和对 Agent 失败的观察，而不是亲手写几十万行代码。也许模型本身最终会补上现在人类专家提供的判断。Anthropic 在那份研究最后也专门提到，他们正在观察“expertise 的收益是否会随着模型进步而下降”；如果有一天这种收益真的持续下降，那么今天我们还能保留下来的这部分人的价值，也未必稳固。

**十三、全文的落点**

作者最后回到自己的经历：2016 年，他看到开源软件和云计算让一个人可以做过去一个团队才能做的软件。2023 年，他看到 ChatGPT 已经可以当 Driver 写大量代码，但仍觉得人的 Review 不可替代。2024 年以后，他开始越来越少亲自写代码，把自己放到更高层的架构和设计位置，那时他已经把这种方式称作 AI 驱动开发。而现在，他发现连 Review、测试、Debug、生产故障调查这些原本属于软件工程师核心职责的工作，也在不断离开人。

他并没有感觉软件因此变简单了。Free4Chat 比以前复杂得多，策引也比以前复杂得多。代码更多，系统边界更多，真实用户和真实生产问题也更多。奇怪的地方恰恰在这里：软件仍然在越来越复杂，但这种复杂度已经不再要求同比例增长的人类工程劳动。

这也许才是 Agent 时代真正重要的变化。过去我们通常默认：软件越复杂，需要的软件工程师越多。未来这个关系未必成立。

所以真正值得问的，已经不是“AI 会不会取代软件工程师”，而是一个更基础的问题：复杂的软件，还需要和过去一样多的软件工程师吗？

以及那个作者现在反而越来越在意的问题：如果以后真的只需要少数有经验的人带着一群 Agent 工作，那么这些“有经验的人”，又是从哪里来的？

这两个问题，前者关于数量，后者关于传承。前者回答的是“现在还需要多少人”，后者回答的是“未来还能不能长出这样的人”。文章的价值，就在于它没有停在“Agent 很好用”或“程序员要失业了”这种表层判断上，而是用两个真实、复杂、长期维护的项目，把软件工程正在发生的结构性变化摊开来看：实现层在退人，Review 和调查也在退人，人集中到产品方向、成本、体验和责任这几个高后果决策点上；而注意力取代时间成为新瓶颈，经验从生产能力变成风险控制能力；最后，最棘手的问题是，这套依然依赖经验的工作流，可能正在削弱经验自身的再生产路径。
