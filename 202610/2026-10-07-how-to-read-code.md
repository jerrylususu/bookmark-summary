# How to read code
- URL: https://www.seangoedecke.com/how-to-read-code/
- Added At: 2026-10-07 05:51:25
- Tags: #read #guide

## TL;DR
文章认为读代码不能像读书按序读，应借鉴数学论文多轮分层扫描：先追关键路径建流程，再细看并最后通读，聚焦目标；AI不能替代读代码，LLM输出也须审查。

## Summary
这篇文章的核心观点是：读代码不能像读书那样按顺序从头读到尾。作者认为代码和自然语言文本有三点根本不同。第一，英文写作是为人类阅读设计的，作者可以按任何顺序安排内容；代码却是为计算机运行设计的，顺序主要由机器约束决定，不能为了可读性随意挪动一行。第二，英文通常读最终成品，代码却常常读 diff——工程师大部分时间是在看对已有代码的细微修改，而不是全新程序。第三，代码的结构复杂度远高于自然语言，调用关系、依赖关系可以跨越整个代码库，而且大型代码库的规模极大。因此，大型程序超出一个人能完全理解的范围，读代码本质上是一种妥协：决定哪些部分深挖，哪些部分略过，把有限脑力分配到不同区域。很多人读得很差：像读书一样硬着头皮从头读到尾，结果丢失执行流程；或者只看 diff，忽略未修改部分的重要性；或者被复杂性打败，直接靠猜。

作者自己的方法借鉴了读数学论文的“dyadic scanning”，也就是多轮、分层扫描。他不按顺序慢读，而是做多遍快速扫描：先选一条重要路径，例如 diff 引入功能的 happy path，追踪哪个函数调用哪个函数，先建立整体流程感。之后才仔细看这些函数具体做什么。通常他会做多轮，每轮追不同线索：拿一个函数或一块数据，看它如何被使用，展开到多个调用点，包括 diff 之外的调用点。小 diff 用 ctrl+f 搜函数名跳转；大 diff 在编辑器里 ctrl+click 导航。每轮都只专注当前目标，其他全当黑盒。等确信自己理解了这个 diff，他才从头到尾仔细读一遍。这一遍不是为了学结构，而是为了抓之前乱序扫描漏掉的怪异代码。如果发现异常，再回到多轮扫描。这样听起来慢，但每轮都很快，因为不需要逐行死磕。

关于 AI，作者反对“现在不用读代码了”的说法。无论是相信 LLM 能可靠生成无需监督的优质代码，还是让另一个 LLM 替你审查代码，他认为都不成立。LLM 代码质量取决于场景；自用工具可能可以不读，但实际 AI 生成代码仍然必须读。他经常发现 AI 代码中的巨大错误。这些未必是 bug，因为代码通常做了 AI 想做的事，但存在对齐问题：AI 的技术价值观和你或公司不一致。比如一个小改动为了传递额外值，因为 agent 发现一个设计上无害的竞态条件，就膨胀成三千行复杂修复。LLM 也不能替你读代码，原因相同：即使不犯错，它的技术判断也不等于你的判断。可以用 LLM 辅助阅读，但必须审查它的输出，同时自己仔细读代码。

脚注补充了几点：现实中读书也常跳读或不过脑；代码顺序的首要约束是计算机，能运行比可读更重要；伟大文学的句法解析也很难，一句话可改变许多句子的意义，类似函数有很多分散调用者；只看 diff 忽略未改部分是代码审查的主要错误；作者讨论的是几百行以上的有意义 diff，琐碎 diff 可以端到端读。
