# How our vibe coded website looks like a designer made it
- URL: https://railcode.dev/blog/vibe-coded-website
- Added At: 2026-10-18 13:50:44
- Tags: #read #design

## TL;DR
作者用 AI 编码代理做网站，靠先定概念、按强度光谱多次生成并“放飞”、频繁 fork 对比、playground 调参和大量参考迭代，证明编码代理也能做出有个人品味的设计，关键是过程好玩。

## Summary
这篇文章讲的是：作者用 AI 编码代理（vibe coding）做了一个网站，结果很多人以为他请了设计师。他想说明，编码代理不仅能生成千篇一律的“AI 味”页面，也能做出有个人品味的设计。

**起点：先有一个概念**

Railcode 的名字来自“code on rails”（代码跑在轨道上），产品替用户托管基础设施和护栏（rails）。作者发现用户和自己都在里面玩得很开心，于是“rails + fun = 过山车”，决定网站里要有过山车。

他不是设计师，很难凭空造概念，所以靠两种方式找灵感：浏览大量喜欢的网站；让代理按不同风格批量生成同一个东西的设计。大多数时候是死路，但能打开思路。

**关键方法：强度光谱和“放飞”**

他会让代理把同一个概念做成从极简到夸张的一串版本，判断这个方向整体是否有意思，以及该走克制还是夸张路线。每个概念至少做 4 个版本，有时 10 个；一半给明确指导，另一半让代理“go wild”。放飞出来的东西通常很烂，但能提供火花。比如那个丑陋的霓虹设计他绝不会用，却把他从 ASCII 风格推向更大胆的方向。

**从单个过山车到整个乐园**

霓虹设计让他想起童年游戏《过山车大亨》，于是先让 Fable 做了个可玩的迷你游戏（并行两个版本，一个透明背景）。玩了一会儿觉得网站里放游戏太重，退回只做一个满意的过山车。把过山车贴到模板上后，发现它孤零零杵在页面中间很奇怪，于是决定做一整座乐园。

他先在 hero 底部加了一条约 200px 高的游乐设施条带，直接放到网站上仍然很丑。迭代方法是：让所有资产的设计风格锚定在那辆过山车上，手工挑选和调整每个动画，并让这条带子不再是独立元素，而是作为通向下一区块的颜色过渡。

**Fork 和 playground**

在设计基本定稿前，他坚持只用一个 HTML 文件，之后再拆成 React 组件。这样 fork 一份设计、改一两处、并排比较非常快，而且从不删除任何 fork。他还会让 Claude 做“playground”，实时调颜色、字体、位置等变量。比如草地一开始是蓝色，改成绿色后不满意，就用 playground 试出想要的那种绿。

**细节决定成败**

早期让 Fable 生成的一批“开发者工具趣味网站” mockup 大多是垃圾，但后来做 CTA 时，他从其中一张里找到了可用的灵感——这说明早期大量看设计是有价值的，哪怕当时很糟。白色背景不够有趣，改成天蓝色再加云，效果立刻不同。主视觉定调后，其余部分跟着展开：产品强调色本来是蓝色，但网站上的绿色是自然长出来的，他索性拥抱绿色，做出浅绿、深绿区块和土壤页脚，甚至考虑回头改产品设计。导航也试了白、浅蓝、浅绿、深绿四种静态色，最后决定让它随所在区块的背景色变形。

**灵感来源**

他大量参考现有网站：浅色转深色的区块参考 Contextual AI，某个区块参考 Clay，插画与内容的结合感参考 Sentry——哪怕最终成品和 Sentry 完全不像。半夜还在给代理发“more”，要求继续迭代。

**他总结的可复用经验**

- 设计只用 Anthropic 的模型，认为 OpenAI 模型即使给具体指令也很吃力，Fable 最好。
- 定稿前始终一个 HTML 文件，之后才处理文案等。
- 大量看网站，喜欢某个组件就以它为基底继续搭。
- 一开始生成海量网站，99% 扔掉，偶尔捡回一个组件或一个新想法。
- 让代理“放飞”，并按从极简到离谱的光谱做多个版本。
- 频繁 fork、对比、保留所有分支，形成可追溯的过程记录。
- 用 playground 实时调参，而不是反复让代理改。
- 无限迭代，多数迭代是死路。

最后他强调，最重要的是整个过程很好玩。
