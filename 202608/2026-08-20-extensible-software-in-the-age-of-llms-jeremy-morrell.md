## TL;DR
LLM 让用户用自然语言生成扩展，Web 软件应从封闭产品转向“可扩展平台”。关键是提供稳定核心与安全隔离，采用对象能力而非暴露凭证，并借助 V8 Isolates、MicroVM、WASM 等原语控制成本与风险。

## Summary
这篇文章从一个观察出发：现在大多数 Web 软件是“静态”的，开发者资源有限，只能优先做最大用户群需要的功能。需求曲线头部被服务得很好，但每个用户都有不同的长尾需求；如果为了长尾不断加功能，界面会复杂到不可用。

LLM 辅助编程的出现，让“为一个人做软件”（Software for One）变得非常容易，个人可以把自己工作流中的小需求直接“说出来”并生成代码。Y Combinator 的 Pete Koomen 也提出了“Small Software”的概念，认为创建个人工具已经很容易，但部署、安全、分享仍然困难。Pi 这类“LLM 原生软件”代表了新方向：有一个经过打磨的核心，同时允许用户通过自然语言生成扩展，并且可以分享这些扩展。

作者因此提出核心假设：Web 上存在“可扩展软件”的新机会。LLM 大幅降低了编写扩展的成本，现代沙箱技术降低了部署成本和安全风险。应用可以提供一个稳定、可问责的核心，让用户安全地向各个方向扩展；也就是“给用户超能力”。

文章列举了几个适合这种模式的场景：

- AI Agent：Pi、DeepSeek、opencode 等正在实验，但目前用户多为技术人员，组织也不一定放心运行无人审查的软件。真正需要的是让医生、律师、会计等非开发者也能安全定制工具。
- 企业内部平台：员工需要查看、查询、关联各类数据。与其让员工各自“vibe coding”再部署到 PaaS，不如给一个受控环境：没有可泄露的密钥、数据访问由平台团队统一管控、合规和安全有保证。
- 支持平台：支持人员可以创建扩展，在工单界面显示特定系统数据、自动启动第一轮调查、添加“重置配额”等按钮，并分享给团队。
- 可观测性平台：日志搜索、追踪瀑布图等现有功能对请求/响应型系统够用，但现代系统更动态、有状态，用户需要自定义可视化、注入自己的逻辑，例如数据清洗、定时告警、部署时执行脚本、把日志中的资源 ID 变成外部链接。

文章强调，在 Web 上做可扩展软件比本地软件难得多。以 Obsidian 为例，插件能力极强，但代价是必须完全信任每个插件，插件可以读取、外传数据甚至做恶意操作；对于笔记软件这个风险可以接受，但对客户数据、财务数据、私信等系统就不行。执行任意代码会带来崩溃、无限循环、密钥泄露、数据外泄、DoS、Spectre 攻击、挖矿滥用等一堆问题。

然后文章指出 Salesforce 是一个被忽视的成功先例。它不只是 CRM，而是一个多租户可编程平台。自 2007 年起，它让用户在平台内运行 Apex 代码：可以定义 REST 端点、定时任务、在事务和事件中插入自定义逻辑。它没有现代容器，只能自己构建编译器、类型系统、运行时、标准库等，但因为解决的企业问题足够有价值，所以能形成一个生态。作者认为可以借鉴它的思路，但不必照搬技术。

要实现这种平台，需要一个新原语，必须具备几个属性：

1. 经济运行：不能为每个用户启动一个容器，空闲时应接近零成本，单次执行成本极低。
2. 快速冷启动：如果用户代码在请求关键路径上，冷启动应以毫秒计。
3. 可控制限额：必须对 CPU、内存、网络请求、响应大小、日志量等设置限制，防止用户代码失控。
4. 强隔离边界：无论崩溃、无限循环还是恶意代码，都不能影响其他租户或逃逸，包括防 Spectre 等推测执行攻击。
5. 允许代码安全行动：不能让代码完全无法做事，也不能直接暴露 API 密钥和任意 fetch。

文章重点讲了“安全行动”的模型演进：

- 纯函数最简单安全，但能力有限。
- 直接 fetch + API key 很危险，恶意代码可以把密钥 POST 给第三方。
- 使用代理替换 token、加目的地址白名单和限流，比直接 fetch 好，但仍有问题。如果要对单个资源做细粒度限制，代理过滤逻辑会变得非常复杂，难以保证安全。
- 更好的方式是对象能力（object capability）：不暴露环境 I/O，只把具体函数引用传给不可信代码。代码只能通过传入的能力做事情；API 凭证从不暴露，也无法泄露数据。例如 IFTTT 给用户的是 `twitter.post_new_tweet()`，而不是 Twitter API key。这种形式也更容易让 LLM 从 TypeScript 定义生成代码。

最后，文章比较了技术实现选项：

- 解释器：如 Lua、QuickJS 或自研，Salesforce 当年的路线，今天仍可用。
- V8 Isolates：谷歌在 V8 上投入巨大，Cloudflare Workers 用它作为隔离边界；还有 Cloudflare Dynamic Workers、Node 的 `isolated-vm`、Rivet 的 `secure-exec` 等。
- MicroVM：Firecracker、libkrun、AWS Lambda MicroVM、`@deno/sandbox`、smolvm、Tensorlake、Daytona 等。启动在亚秒级、开销小、隔离强，有 POSIX、能跑二进制，适合重计算；但如果只是调用 API、跑工作流，可能过重。
- WASM + WASI：WebAssembly 默认没有网络、环境变量等能力，必须由宿主注入，安全起点好；WASI 定义宿主向不可信代码传能力的标准接口。可以支持多语言编译，但工具链更复杂。WASM 也可以跑在 V8 isolate 或 MicroVM 里，并不互斥。

文章接近结尾时强调：如果隔离原语本身没有能力模型，仍然可以用对象能力协议，比如 Cap'n Web，来配合这些原语。作者还暗示 Cloudflare 的 Dynamic Workers 是特别适合这个模式的选择。整篇的核心是：LLM 让“用户说出需求、代码自动生成”成为可能，Web 软件应该抓住这个机会，从一个封闭的静态产品，变成有坚实核心但可被安全扩展的平台；而安全扩展的关键是有好的隔离原语，以及基于“能力”的访问控制，而不是暴露凭证。
