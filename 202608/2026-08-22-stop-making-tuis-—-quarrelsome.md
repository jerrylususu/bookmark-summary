# Stop Making TUIs — Quarrelsome
- URL: https://sockpuppet.org/blog/2026/08/20/stop-making-tuis/
- Added At: 2026-08-22 14:41:44
- Tags: #read #ui

## TL;DR
文章认为，AI编程助手已让原生GUI开发变得容易，不应再继续构建终端用户界面（TUI）。作者逐一反驳TUI的密度、SSH、可访问性等优势，并展示用AI生成的macOS应用，呼吁开发者更新默认选择，转向原生GUI。

## Summary
这篇文章的核心观点是：**我们不应该再继续构建终端用户界面（TUI），而应该转向构建原生图形用户界面（GUI）**。作者认为，随着 AI 编程助手的成熟，以前很难、很繁琐的原生 UI 开发已经变得容易，因此没有理由再忍受 TUI 的种种限制。

作者首先展示了自己最近用 AI 辅助构建的一批原生 macOS 应用，包括 Markdown 查看器、SageMath 计算器前端、音乐播放器、自驱动 wiki、食物宏量追踪器、温度菜单栏工具和 Apple TV 遥控器。他在这些项目里几乎没有手写 UI 代码，而是通过给 Claude 或 Codex 下达指令，让 AI 生成 SwiftUI 界面。这些应用虽然设计上不算惊艳，但已经足够实用，而且远超他过去对 UI 代码的预期。他由此引出一个问题：这到底算开发软件，还是只是在配置自己的电脑？

接着，作者区分了 CLI（命令行接口）和 TUI（终端用户界面）。他认为 CLI 在很多场景下仍然是不可替代的，比如脚本化、自动化、远程操作等；但 TUI 几乎从来都不是必需的。TUI 的诞生源于 1970 年代的电传打字机和哑终端限制，后来延续下来主要是因为调制解调器（需要低带宽文本界面）以及 Unix 极客不愿意学 Motif 这类 GUI 工具包。现在这些历史原因已经不成立了。

作者逐一反驳了为 TUI 辩护的常见理由：

- **“TUI 信息密度高、操作快、键盘友好”**：这些优点并非 TUI 独有，GUI 也可以做得很密集、很高效，比如 Bloomberg 终端。既然现在 AI 让 GUI 开发变便宜了，我们应该去探索如何把 Magit 或 Lazygit 的优点搬进原生 GUI。
- **“TUI 可以通过 SSH 使用”**：实际上你通常不需要在生产服务器上跑 UI，你需要的是远程 CLI，然后在本地用 GUI 驱动它。Emacs TRAMP 就是一个好例子，它把 SSH 隐藏起来，提供原生的图形编辑体验。
- **“TUI 对可访问性更好”**：这个说法可能不成立。现代 GUI 框架（如 SwiftUI）从设计上就考虑了可访问性，而 TUI 的屏幕阅读器体验往往很糟糕（例如会逐行读出边框字符）。可访问性不是偏好 TUI 的理由。
- **“TUI 跨平台”**：对作者个人来说不重要，因为他构建应用是给自己用的，不是为了发布给 Linux 用户。而且 AI 也能生成 Windows 和 Linux 的原生 UI，只是他暂时没有环境去验证而已。

作者还分享了自己的原生 UI 开发流程：收集一些针对 macOS 设计的 AI 技能包（如 SwiftUI 技能、macOS 设计技能），启用 computer-use 让 AI 能自己运行和调试应用，并使用纯 Makefile 构建以避免打开 Xcode。他有一个模板目录，每次新建项目就复制它，然后告诉 AI 想做什么。他说同样的方法也能用来构建 TUI（让 AI 用 tmux 测试），但自己以后可能不会再想构建 TUI 了。

最后，作者呼吁：即使你以前是系统程序员、从不写 UI 代码，或者只写过用 ASCII 字符画窗口的界面，现在也应该重新校准。因为 AI 已经打破了“前端/后端”、“Web/原生”的壁垒，你可以合理地默认构建原生用户界面，而且效果还不错。如果你以前喜欢 NetNewsWire、Transmit、Little Snitch 这类优秀的原生应用，却一直没尝试自己做，那你正在亏待自己。去构建一个原生 UI 吧，它可能会改变你的思维方式。

整篇文章带有明显的个人色彩和幽默感，作者并不否认自己对 TUI 有偏见，但他更想强调的是：**技术条件已经改变，我们应该更新默认选择**。
