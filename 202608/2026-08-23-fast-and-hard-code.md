# Fast and Hard Code
- URL: https://lucumr.pocoo.org/2026/8/22/fast-hard-code/
- Added At: 2026-08-23 12:05:33
- Tags: #read #llm

## TL;DR
LLM降低了编程语言转换成本，使更多开发者敢于选择Rust、Zig等性能更好但更难的语言及DWARF、eBPF等底层技术。这可能带来两极分化：既产生更多低质量代码，也催生更多追求极致性能和小体积的开发者与项目。

## Summary
这篇文章主要讨论了一个趋势：在大语言模型（LLM）和编程代理（agent）的帮助下，编程语言的“易用性”不再像以前那么关键，因此越来越多的人开始选择更“难”但性能更好、体积更小的语言和技术，比如 Rust、Zig，以及 DWARF、eBPF 这类底层技术。

作者首先从 Twitter 上的一个梗说起：“编程已经被解决了。”虽然他不确定这个说法有多少真实性，但有一点很清楚：熟悉一门语言这件事不再那么重要了，而且过去对人类程序员很重要的那些“摩擦”，对 AI 代理来说并不存在。也就是说，LLM 让语言选择变得不那么有后果——如果你不喜欢某个语言的选择，几乎可以轻松地让 AI 把代码重写成另一种语言，甚至选择一门你完全不了解的语言。这样一来，人们可以更多地根据语言的“营销”来做选择，而不是基于自己是否熟悉。

作者以自己作为长期 Rust 程序员的观察为例：现在有很多人开始发布 Rust 代码，而这些人以前可能根本不会选择 Rust。他认为这至少部分归因于两种近期的氛围转变：一是人们越来越多地谈论“想要更快的软件”；二是 LLM 在“不改变行为的前提下优化代码”方面表现得非常出色。像 Mitchell Hashimoto、Charlie Marsh、Jarred Sumner、Daniel Lemire 等人一直对高性能软件有执念，同时也都愿意接受 AI 代理来写代码。或许正是因为这样，其他人也开始加入。借助 autoresearch 这类工具，你甚至不需要知道所有优化技巧，只要派一个代理去研究就行——当然，具备相关知识会大有帮助。

接着作者指出，现在有很多项目都想做到“又快又小”，并且越来越倾向于选择“硬语言”。受益的不只是 Rust，还有 Zig——尽管 Zig 的创造者和核心社区里有一部分人对 AI 这件事相当反感。作者举了两个例子：Cloudflare 新推出的 Artifacts 服务使用了一个纯 Zig 编写的 Git 协议引擎，编译成大约 100 KB 的 WebAssembly 模块；Vercel 发布了 fx，一个用 Zig 编写的编程代理，宣称“小且快”。据作者所知，这些项目很大程度上都是 LLM 辅助完成的。

然后作者说，不只是人们在选择不那么常见的语言，而且他们也在越来越多地接触“难得多”的技术。他突然看到人们用 DWARF 调试文件、eBPF、自定义网络驱动、自定义加密，还有很老的计算机硬件做出了一些令人印象深刻的成果。以前这些领域对很多开发者来说都是禁区。在有些情况下（比如加密），甚至会被懂行的人有意“把门关上”。

最后作者总结：也许这个世界会产生更多的“垃圾代码”，但也可能因此出现更多想要软件又快又小的开发者。

简单来说，这篇文章的核心观点是：LLM 降低了编程语言和技术栈的转换成本，让更多普通开发者敢于进入高性能、底层、传统上被认为困难的领域；这可能会带来两极分化的结果——更多的低质量代码，但也可能催生更多追求极致性能和小体积的开发者与项目。
