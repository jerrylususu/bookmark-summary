# When in doubt, flail about
- URL: https://www.seangoedecke.com/when-in-doubt-flail-about/
- Added At: 2026-11-23 15:13:58
- Tags: #read

## TL;DR
信息不足、目标不清时，主动“乱试”比谨慎等待更有效：多尝试、细看反馈、无情放弃无效方案；产品、工程、组织问题皆适用，内心不适是正常信号。

## Summary
这篇文章的核心观点是：当你处在信息不足、目标不清、不知道该做什么的情况下，与其谨慎等待、试图先彻底理解全局，不如主动“乱试一通”（flail about）。作者承认这是危险建议：乱试得不好会显得你净出馊主意、损害职业声誉；但如果方法正确，它反而是最快获得理解、变得有用的方式。

作者说的“乱试”不是盲目乱来，而是三条原则：第一，尝试很多不同的事情；第二，非常仔细地观察反馈；第三，毫不留情地放弃没有正反馈的事情。多试之所以关键，是因为你此时本来就没有能力判断什么是对的，大多数计划都会很糟。只试一个，很可能押错；试十个，才可能有一个靠谱。同时，手里有很多计划，你才不会对某一个计划过度投入，才能及时丢掉失败方案。你需要同时对两类反馈敏感：身边更有经验的人的反应，以及现实本身的结果，比如延迟有没有下降、用户指标有没有提升。理想情况下，没有“哇”的反馈就放弃。

文章把“乱试”分成三类。第一是产品上的乱试：做还没有产品市场契合的新功能时，所有人都不确定，你可以在核心想法周围试很多边缘方向。作者举例说，他在 GitHub Models 上做过很多没成的功能和集成，但“让 AI 推理通过 GitHub Actions token 运行”这个尝试意外地有粘性，后来成了 Continuous AI 的种子。新产品里如果不乱试，往往会把大量精力投在注定失败的点子上；更好的做法是试到某个方向有牵引力，再全力投入。

第二是工程上的乱试：有些系统太复杂、太纠缠、太大或太陌生，先完整理解再改并不现实。作者认为现代大型软件系统变化太快、太复杂，逐个吃透再提改动很愚蠢。更实际的是做一批试探性改动，看代码或性能表现如何；不像改进就立刻丢掉，像改进再深入查为什么。

第三是组织上的乱试，作者认为这最贴合高级和资深工程师：问题不是技术问题，而是两个团队不沟通、某团队不满意、总监或 VP 也说不清原因。这时可以试一堆可能有用的事：自动化部分手工工作、主动接手任务、提出可能改善局面的长期计划等。多数不会有用，但至少表明你在努力，这在组织情境里很重要。不过这里最需要敏感反馈：如果某个行动失败就立刻放弃，你能建立信任；如果忽视反馈还硬推，别人的不满和怒火就会转向你。

文章最后解释为什么叫“flailing”：因为它从内部感受上就像乱扑腾。经理可能看到的是一个主动实验方案的工程师，但你自己会感觉在不断失败、信息不足、试一堆没用的东西、像在出丑。这种不适感是正常的，必须忽略。作者说，这种“我在乱试”的难受感是成为有效工程师要穿过的心理障碍之一；提前知道会有这种感觉，就能把它识别为积极信号，而不是“我出问题了”的信号。只要你对反馈敏感、愿意立刻放弃无效计划，乱试就是应对困难工程和组织问题的一种非常有效的方法。
