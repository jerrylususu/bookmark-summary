# 使用形式化方法找出网络模型中的竞态问题
- URL: https://coderemixer.com/2026/11/17/deskfleet-network-in-quint
- Added At: 2026-11-17 15:41:25
- Tags: #read #guide

## TL;DR
作者用Quint对DeskFleet异步竞态建模，以抽象拆分和最小基数验证，发现Promise缓存锁死与all提前reject竞态并修复；认为形式化可提前证伪异步设计死角，AI显著降低门槛。

## Summary
这篇文章是作者用形式化方法（Quint）给 DeskFleet 这个 P2P 远程管理工具排查网络竞态问题的一次实践记录。核心逻辑可以分成四层：为什么要做、用了什么工具、怎么建模、发现了什么以及学到什么。

## 一、出发点：两个真实 bug

作者先摆出两段看起来没问题、单元测试也能过的代码：

**Case 1：清理 Promise 被缓存，导致机器永久锁死。**
`#revocation` 缓存了 `Promise.all([closeAll(), save revoked])` 的结果。一旦 `#save` 或 `closeAll()` 出现临时 I/O 失败，这个 Promise 就变成 rejected 状态并被永久保留。之后每次 `enroll()` 执行 `await this.#revocation` 都会立刻抛错，既不重试也不清除，除非重启整个 daemon。

**Case 2：`Promise.all` 提前 reject，留下“幽灵 Peer”。**
`Promise.all` 在第一个分支失败时就立刻 reject，不会等另一个仍在执行的分支结束。如果 `closeAll()` 先拒绝，而旧的 `#save()` 还在写 `central.json.tmp`，此时重新 `enroll()` 并写入新凭证，新旧两次 `#save()` 就会发生文件竞态覆盖，产生关不掉的旧 Peer。

这两个 bug 的共同特征是：**单看每段代码都合理，靠 Code Review 和单元测试都发现不了，只有多端异步交错时才会暴露**。DeskFleet 从 v0.1.0 到 v0.18.1 几乎每个版本都在修这类 corner case。

## 二、工具选型：为什么是 Quint 而不是直接用 TLA+

作者的问题是“多进程/多节点异步交错下，协议规则之间是否会互相冲突”，而不是“算法在任意 N 下是否收敛”。TLA+ 属于自动化状态空间搜索，能吐出具体的反例轨迹，但语法太数学、脱离静态类型，即使是 AI 也很难照着现有代码写对。

Quint 的价值在于：

- 语法几乎和函数式 TypeScript / Rust 对齐，规格文件和实现可以放在同一个 PR 里被同一批 Reviewer 理解；
- 语义上站在 TLA+ 肩膀上，编译后交给 Apalache（基于 Z3 SMT）做实际的模型检测；
- 支持两种运行模式：`quint test` 用内置 TS 仿真器跑固定种子抽样和确定性回归，几秒出结果，适合日常 CI；改动动作规则时切到 `quint verify`，交给 Apalache 做有界全路径搜索。

## 三、建模：抽象 + 正交拆分 + 最小基数

建模时先把现实细节剥掉：DTLS、ICE、TURN、Mux 信用帧这些全部留在实现里，模型只关心**授权、信令连接、节点租约、路由所有权**。物理时钟也被去掉，用状态机替代，超时直接抽象成随时可能触发的动作（`reservation_due`、`authorization_due`、`link_dead` 等），这样状态空间天然有限，改超时时长也不会让模型失效。

然后是关键的工程经验：**不要造一个大模型**。作者最初把所有东西塞进一张宽 Grant 映射，Apalache 跑了约 12 分钟；把只写一次的 Binding 拆出来后才压回 5 分钟。最终在 specs/ 下切出 8 个独立小模型，每个维度的基数都压到“能产生竞争的最小值”：

- 2 个 Peer：1 个测不出并发隔离性，2 个刚好能验证“吊销 p1 不误伤 p2”和“旧 Peer 失败后新 peerId 不串号”；
- 2 个 API 节点 + 2 代连接身份：够表达跨节点抢占路由、故障节点自我隔离后由健康节点接管、旧连接迟到帧被新身份围栏拦下；
- 2 条逻辑流：够验证关闭一条流不连坐兄弟流，而底层 Peer 吊销要同步释放全部流；
- 2 代凭证：覆盖“旧 Token 被吊销 → 重注册拿新 Token → 旧 Token 的迟到 401/4401 不得撤销新凭证”的代际隔离；
- 4 帧 FIFO 队列：刚好同时装下“1 个在途 Offer + 2 次通知 + 1 次心跳快照”，再大不会产生新语义，只会拖长 SMT 求解时间。

这就是形式化验证里常用的 **Small-Scope Hypothesis**：绝大多数并发协议漏洞，不需要成百上千个节点，只要存在“能产生竞争的最小基数”就会暴露。

## 四、验证发现的问题与修复

文中给出的两个修复正好对应开头的两个 bug：

**修复 Case 1：失败后按次重试清理。**
```ts
try { await this.#revocation } catch {
  // 清理失败不能阻塞后续每次 enroll，趁故障可能已清除，现在就重试
  this.#revocation = this.#retire()
  await this.#revocation
}
```
重试机制意味着：一次失败只影响这一次 enroll，不会永久锁死。

**修复 Case 2：用 `Promise.allSettled` 等两个分支都结算完。**
```ts
async #retire(): Promise<void> {
  const results = await Promise.allSettled([
    this.#peers.closeAll(),
    this.#credentials ? this.#save(this.#credentials) : undefined,
  ])
  const failures = results.flatMap(r => r.status === "rejected" ? [r.reason] : [])
  if (failures.length === 1) throw failures[0]
  if (failures.length) throw new AggregateError(failures, "Revoked machine cleanup failed")
}
```
只有两个步骤都真正结束后才算结算，避免旧 `#save` 还在写文件时新 enroll 就覆写。

**服务端对应修复**：`revoke_failed_setup` 先把撤权持久化，然后**无条件**通知 daemon 和 owner。原因是并发撤权可能先于本请求到达 daemon、什么也没关掉，而 store 只返回“新撤销”的 grant，所以必须对这个 grant 再补发一次通知。信令 offer 末尾也统一把 401/403/404 这类“已撤权”错误收敛到 `revoke_failed_setup`。

## 五、作者的核心结论

架构设计通常躺在 Markdown 文档和工程师的口头共识里。自然语言有个天然缺陷：人脑读文档时会自动脑补“正常路径”，极难察觉两条看似合理的规则在边界条件下会互相冲突。而复杂网络系统真正的噩梦是**异步交错**——断网、重启、队列积压、消息乱序、超时、重试以极罕见顺序叠在一起。这种场景：

- Code Review 看不出来，因为单看每段代码都对；
- 单元测试很难测出来，因为 Mock 出来的都是人能想到的已知异常。

TLA+/Quint 这类方法并不保证代码绝对无 bug，它管不到编码手误、内存溢出或真实网络抖动。它真正带来的价值是：在**最难靠直觉推理的异步协议与架构设计层**，把原本只能靠线上事故撞出来的逻辑死角，变成可以提前推导、被机器证伪、并随代码一起演进的工程确定性。

最后作者强调 AI 极大降低了门槛：过去做这种事往往需要找几个 PL 方向的 PhD 研究一两个月，人员一变动就没人维护；而这个 PR 的证明只靠 Grok 4.7 和 GPT-6 Astra 花了一天就推进到找出具体 bug 并修复，说明把形式化证明融入日常开发已经高度可行。
